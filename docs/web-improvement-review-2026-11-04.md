## 먼저 결론

화면 디자인이나 추가 타이머보다 **새 화면인지 확인하고, 끊긴 동안의 관측을 무효화하는 처리**가 우선이다.
프레임 수신·분석·타이머·알림·화면 표시를 분리하면 사용자가 말한 '다른 탭/오래 켜 두면 인식이 안 됨'을
구분해서 진단하고 복구할 수 있다. 현재 코드만으로 사용자의 정확한 장애 원인을 단정할 수는 없다.

우리 앱에는 이미 정밀 야누스/파운틴, 숫자 합의, 마지막 프레임 시각 보정, PIP,
프리셋, 알림 설정, 진단 클립이 있다. 이를 없는 기능으로 보고 다시 만들 필요는 없다.

## 1. P0: 멈춘 화면을 정상 감지 입력으로 계속 쓰지 않기

### 확인한 코드

- `src/capture/screenCapture.ts:205`: `refresh()`는 보관된 프레임이 있으면 새 프레임이 없어도 `true`를 반환한다.
- `src/engine/engine.ts:75`: 이 반환값과 공유 상태만으로 `live`를 계산한다.
- `src/engine/engine.ts:85`: `watch`도 프레임 신선도가 아닌 `live`와 암전 상태로 결정한다.
- `src/engine/engine.ts:127`: 룬/사냥 멈춤에 같은 `live`를 전달한다.
- `src/engine/engine.ts:141`: 10초 무수신 경고는 감지 후에 계산하며, 감지를 중지시키는 조건으로 쓰지 않는다.

### 영향

마지막 화면이 남아 있는 동안 오래된 입력을 여러 번 처리할 수 있다.
시간 경과를 판단하는 사냥 멈춤에서는 화면 수신 중단이 실제 사냥 중단으로 잘못 해석될 수 있다.
이는 경고 표시를 추가했던 기존 수정에 남은 공백이다.

### 개선안

- 화면마다 `sessionId`, 증가하는 `frameId`, `receivedAt`을 부여한다.
- 공유 연결 여부, 새 화면 도착 여부, 관측 신뢰 여부를 별도로 관리한다.
- 새 `frameId`일 때만 감지/학습/합의에 입력한다. 타이머와 알림 스케줄은 별도로 진행한다.
- 오래된 화면이면 '화면 수신 대기'로 전환하고 새 관측을 요구하는 판정을 멈춘다.
- 이미 확인한 버프/스킬 종료 시각의 알림은 무조건 지우지 말고, '예측 중'으로 표시해 정책을 분리한다.
- 캡처가 계속 전달하는 정적인 게임 장면과 전송 자체가 끊긴 상황을 픽셀 동일성만으로 혼동하지 않는다.

검증 기준: 프레임 공급을 끊어도 같은 프레임의 판독/학습 횟수는 늘지 않고,
수동 일반 타이머와 이미 확정한 일정은 정책에 맞게 계속 동작해야 한다.

## 2. P0: 끊겼다 재개할 때 사냥 감시 기준을 새로 잡기

### 확인 및 개별 함수 검증

`src/engine/runeStall.ts:58`은 `live === false`일 때 감시기를 초기화하지 않고 반환한다.
같은 영역/모드로 돌아오면 `lastChangeAt`이 남아 있다.

`ChangeMonitor`에 첫 화면 → 변경된 화면을 넣어 감시를 활성화한 뒤,
30초를 건너뛰고 같은 화면으로 재개하는 입력을 주었다.
재개 직후 `isStalled(now, 7)`은 `true`였다.
이것은 모니터의 개별 함수 검증이며 전체 엔진이나 실제 게임 재현은 아니다.

### 개선안

- 공유 세션 변경, 무수신, 긴 분석 공백, 영역 변경을 감시 중단 원인으로 명시한다.
- 재개할 때 감시 기준/룬 추적의 재확인 정책을 적용한다.
- 사냥 멈춤은 충분한 새 관측을 확보한 뒤 다시 감시한다. 과거 공백을 사냥 중단 시간으로 합산하지 않는다.
- 같은 공유를 재시작해도 세션 번호를 변경한다. 해상도와 영역 좌표가 같다는 이유로 재사용하지 않는다.

검증 기준: 30초 공유 중단 후 복귀 시 즉시 사냥 멈춤 알림이 나지 않아야 한다.

## 4. P1: 장시간 사용을 위한 진단 녹화 메모리 제한

### 확인

`src/engine/clip.ts:30`은 저장된 유효 영역을 활성 기능 여부와 무관하게 잘라
RGBA `ImageData`로 최근 30초 동안 보관한다. 시간 제한은 있지만 바이트 제한은 없다.
대략 초당 4회, 120회 분량일 때 픽셀 버퍼만 계산하면:

| 영역 한 개의 크기 | 30초 보관 픽셀 버퍼 |
|---|---:|
| 500×300 | 약 68.7 MiB |
| 1000×600 | 약 274.7 MiB |

객체/캔버스/분석용 복사/내보내기 문자열 메모리는 포함하지 않았다.
실측 메모리 사용량이 아니라 보관 형식에 근거한 계산이며, 실제 선택 영역에 따라 달라진다.
여러 영역은 누적되고 겹친 영역도 중복 보관될 수 있다.
`clipSnapshot()`은 전체 기록을 메인 스레드에서 동기 PNG/base64로 변환한다.

### 원본에서 참고할 점과 개선안

설치본에는 메모리 계측과 별도 evidence 인코더 워커가 있다.
Electron의 강제 GC 설정을 웹에서 흉내 내기보다 보관량을 줄이는 쪽이 적절하다.

- 기본 진단 버퍼에 32~64 MiB 등 명시적인 상한을 둔다.
- 켜져 있는 기능에 필요한 영역만 보관하고, 겹치는 영역은 공유한다.
- 중복 프레임을 기록하지 않고 오래된 프레임부터 바이트 단위로 제거한다.
- 압축/내보내기는 워커에서 처리하고 진행률·취소를 제공한다.
- 진단에 버퍼 크기와 실제 샘플 수를 표시한다.

검증 기준: 큰 영역/여러 기능/2시간 실행에서도 정해진 버퍼 상한을 넘지 않아야 한다.

## 5. P1: 화면 표시와 인식 작업 분리

현재 ticker는 워커지만, 실제 템플릿 탐색과 숫자 판독은 메인 스레드에서 수행한다.
근거: `src/engine/buffs.ts:161`, `:194`, `:214`, `src/engine/skills.ts:167`,
`src/engine/booster.ts:47` 및 이를 동기 호출하는 `engine.ts`.

설치본에는 기능별 분석 워커와 `busy`/`timeout`/`stale`/`workerGeneration` 관련 계약 문자열이 있다.
모든 기능이 어떻게 스케줄링되는지 복원한 것은 아니므로 문자열만으로 실제 복구 성능을 입증할 수는 없다.

### 개선안

- 버프칸 탐색부터 분석 전용 워커로 옮긴다.
- 워커마다 동시에 한 작업만 실행하고 밀린 프레임은 쌓지 않는다.
- 결과에 세션/영역 버전/프레임 번호를 붙여 예전 결과가 현재 상태를 덮지 못하게 한다.
- 기능별 최근 처리 시각과 처리 시간, 오류를 보여 준다.
- 워커 실패 시 해당 기능만 재시작한다.

검증 기준: 큰 버프칸 검색/진단 내보내기 중에도 버튼 반응과 타이머 진행이 유지되어야 한다.

## 6. P1: 정밀 스킬에 맞는 준비 체크리스트

### 확인

- 버프: 내장 아이콘 또는 등록 템플릿 + 유효한 탐색 영역.
- '설정 완료'와 '실제로 감지 확인됨'을 구분하고 안내에서 바로 해당 설정을 열 수 있게 한다.

검증 기준: 정밀 스킬만 쓰는 사용자는 퀵슬롯 영역 선택을 요구받지 않아야 한다.

## 7. P2: 인식 정확도 개선은 실제 화면 검증 자료부터

설치본은 버프 탐지·분류·숫자 판독·룬 등에 전용 모델/워커 자원을 포함한다.
우리 앱도 정밀 감지와 숫자 판독을 지원하지만 방식이 다르다.
현 시점에 설치본 모델이 우리 앱보다 얼마나 정확한지는 측정하지 못했다.

권장 순서:

1. 사냥터/해상도/UI 크기/즐겨찾기 위치가 다른 실제 화면 녹화에 정답을 붙인다.
2. 룬 오탐, 버프 종료 알림 누락, 스킬 재사용/연장, 암전, 공유 복구를 별도 측정한다.
3. 현재 엔진을 같은 녹화로 반복 실행하는 회귀 테스트를 구축한다.
4. 가장 많이 실패하는 항목부터 판독기/추적기를 교체한다.
5. 평문 모델과 입출력 명세를 확보하면 모델 어댑터를 추가하고, 기존 방식과 같은 자료로 비교한다.

새 기능보다 '오탐/누락/알림 지연' 수치가 개선되는지를 통과 기준으로 삼는다.

## 8. P2: 설치본에서 참고할 추가 기능

- 게임 영역을 한 번 정한 뒤 내부 좌표를 상대적으로 관리하는 설정 흐름.
  현재는 프레임 해상도와 다르면 영역을 다시 고르게 하며 창 테두리/공유 방식 변경에 취약하다.
  단순 비율 확대만 자동 적용하면 오히려 오탐할 수 있으므로 미리보기와 재확인이 필요하다.
- 사냥 세션·경험치 증가·솔 에르다 기록. 먼저 로컬 저장과 개인 통계로 구현하고 서버 동기화는 후순위.
- 기능별 준비 상태와 최근 인식 시각을 PIP에도 간단히 표시.
- 사냥/보스 프리셋 진입을 단순화. 기존 프리셋/PIP 기능을 활용한다.

원본 사이트의 로그인·일일 이용시간 제한은 원본 서비스의 운영 정책이다.
우리 웹의 인식 개선을 위해 따라 만들어야 할 기능으로 보지 않는다.

## 권장 작업 순서와 검증 범위

1. 프레임 신선도/세션/재개 처리와 합의 중복 제거.
2. 진단 메모리 제한.
3. 정밀 감지 체크리스트 정합성.
4. 분석 워커 분리 및 기능별 상태 진단.
5. 실제 화면 회귀 검증을 바탕으로 자동 인식 개선.
6. 사냥 통계와 추가 편의 기능.

실제 사용 검증은 다른 탭, 가려진 창, 보이는 PIP, 크롬 최소화, 게임 최소화를 각각 나눠 진행한다.
웹 페이지에는 설치본의 `backgroundThrottling: false` 같은 Electron 설정을 적용할 수 없으므로
코드 변경만으로 모든 최소화 상황을 보장한다고 표현하지 않는다.

이번 검토에서 실행한 것은 두 개별 함수 시나리오와 버퍼 크기 계산이다.
게임 실사용 장애의 재현, 사이트에서의 전체 동작 비교, 성능/정확도 실측은 아직 하지 않았다.

## 추가 요구: 데스크톱 앱과 간결한 안내

### 확인한 동작

설치본의 `electron/pickerSources.cjs`는 `MapleStory`와 정확히 일치하는 창을 가장 높은 점수로,
게임명을 포함하는 창을 그다음으로 정렬한다. 게임명이 들어간 Chrome 페이지는 낮은 점수로 분리한다.
`pickFeaturedSource()`와 `pickInitialSelection()`은 마지막 선택을 우선하면서 게임 창을 추천한다.
따라서 **공유 대상 목록에서 메이플이 위에 보이고 미리 선택되는 동작**은 코드로 확인했다.
게임 창 자체를 Windows의 전경으로 가져오는 동작은 확인한 캡처 코드에서 입증하지 못했다.
이를 항상 위에 고정하는 기능과 혼동해서 설명하지 않는다.

웹 PIP는 `src/ui/Pip.tsx`의 Document Picture-in-Picture이고, 앱 자체도 한 창만 관리한다.
Document PIP 명세 §6.5는 탭당 최대 한 창을 정하고 브라우저 전체 제한은 구현에 맡긴다.
따라서 같은 Chrome에서 다른 영상 PIP와 충돌하는 문제를 웹 앱 코드만으로 해결한다고 약속할 수 없다.
근거: https://wicg.github.io/document-picture-in-picture/#one-pip-window

### 제안하는 제품 방향

- **공통 React 화면/인식 엔진 + Electron 데스크톱 배포 + 웹 배포 유지**.
- 데스크톱은 로컬로 패키징한 화면을 로드하고, 캡처·오버레이·창/트레이 제어를 제한된 preload API로 제공.
- 타이머 오버레이는 브라우저 PIP 대신 별도의 항상 위에 있는 Electron 창으로 제공.
  Chrome 영상 PIP와 별도로 사용할 수 있게 설계하고 실제 동시 실행으로 검증.
- 기존 설정은 명시적 내보내기/가져오기 경로 제공. 웹 origin과 데스크톱 origin 저장소는 자동 공유되지 않는다.
- 웹은 설치 없는 실행을 유지하되 캡처 선택/PIP 제약을 지원 범위에 반영.
- 패키징만으로 인식 정확도나 게임 최소화 때의 프레임 생성 문제가 해결되는 것은 아니다.
- 이번 단계는 방향 제안이며 Electron 구현/패키징/배포를 수행한 것은 아니다.

### 기본 화면과 안내 원칙

1. 첫 사용: **메이플 연결 → 사용할 알림 선택 → 소리 확인**의 세 단계.
2. 메인 화면: 기능 이름·켜기/끄기·실제 상태·남은 시간. 일반 설정은 알림 시점·소리만 우선 표시.
3. 자동 감지로 충분한 경우 영역 선택이나 숫자 학습을 먼저 요구하지 않기.
4. 필요한 경우에만 해당 기능 옆에서 한 문장 안내하고 바로 해결 버튼 제공.
   예: '메이플이 켜져 있지 않아요' / '이 아이콘을 한 번 선택해 주세요' / '화면이 멈췄어요 · 다시 연결'.
5. 신뢰도 수치·임계값·글자 학습·분석 로그는 고급/진단으로 옮기기.
6. 짧은 안내는 실행 가능한 기능에 근거해야 한다. 자동 인식이 준비되지 않은 항목을 설명만 숨겨 간단하게 보이게 만들지 않기.

우선 구현 단위는 '메이플 추천 선택 + 공유 + 독립 오버레이 + 간결한 시작 화면'으로 잡고,
그다음 앞서 정리한 프레임/메모리/인식 개선을 공통 엔진에 적용하는 것이 적절하다.
